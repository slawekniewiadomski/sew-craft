# 3D preview of a sewn assembly

- Date: 2026-11-07
- Category: feature (pre-spec exploration)
- Priority signal: medium — the seam record ships first and is useful alone; the
  preview is what makes the seam work legible and is the stated reason for the 3D
  interest.
- Risk signal: medium — a new renderer dependency, a triangulation step and a
  relaxation solver, all behind a derived, read-only view that never writes to the
  document.
- Routing: not ready for a spec. Next: ship
  `.ai/specs/2026-11-07-seams-and-sewability.md`, then `om-spec-writing` for this
  brief. A renderer/solver ADR comes before the spec.

## Problem

The maker can see a flat assembly layout but not the sewn object. For a pouch with
a zipper the layout says nothing about whether the panels close into a shell,
where the zipper ends up, or how large the result is. The seam record already
states exactly what is sewn to what, so a preview needs no extra authoring — only
geometry derived from the pieces and the seams.

The bar is deliberately low: a **dummy** result is useful. No gravity, no
collisions, no self-collision, no time integration, no anatomically matched body.

## Agreed direction

A **read-only 3D preview** opened from the assembly tab. It triangulates each
placed panel's stitch loop, welds the seam sides, inflates the resulting shell
with a pressure constraint, and renders it with orbit controls. A pouch becomes a
rounded pillow; a garment becomes a stuffed dummy. Nothing is stored, nothing is
exported, and the document is never modified.

## Recommended approach — stitched shell + pressure inflation

1. **Panel mesh.** Triangulate each instance's stitch loop in 2D (ear clipping;
   a piece is one simple loop, so no holes). Rounded-corner bridges are part of
   the loop, so the surface is continuous.
2. **Weld.** For each seam, resample every side at the same number of points
   (spacing ≈ 4 mm), paired by normalized arc length from the seam start, honouring
   `reversed`. Merged vertices become shared boundary vertices. Ease is distributed
   evenly along the side; a real sleeve would want it clustered, which is a later,
   additive improvement.
3. **Seed.** The flat layout has zero enclosed volume, so inflation cannot start.
   Offset each panel a few millimetres along its normal, or project the shell onto
   a small sphere, from a fixed seed so the result is reproducible.
4. **Relax.** XPBD with three constraint kinds and nothing else:
   - distance on every triangle edge (inextensible fabric, so panels stay
     developable),
   - a light dihedral/bending constraint (keeps the shell from crumpling),
   - one global pressure/volume constraint (inflates a closed shell).
   30–80 iterations at a fixed step; deterministic. No gravity, no collision, no
   friction, no time-based integration.
5. **Open shells.** A garment has hems and openings. Two options: cap each boundary
   loop with a hidden triangle fan so pressure works, or leave it open and show a
   flat-ish sewn shell. Capping is the "dummy silhouette" trick; a body collider
   (shrink-wrap) is the later upgrade.
6. **Render.** three.js in a lazy-loaded chunk: double-sided flat-shaded mesh, seam
   lines, neutral studio light, orbit + fit, an **Inflate** slider. A pouch with a
   sewn zipper needs no caps at all.

Solver placement: **pure, in `@sewcraft/geometry`** (`drape.ts`), taking resolved
panels and seams and returning positions. The renderer stays thin in the frontend.
That keeps the algorithm unit-testable (determinism, volume increases, edge lengths
preserved within tolerance) and out of the Vue layer.

## Options considered

| # | Option | Cost | Fit |
| - | ------ | ---- | --- |
| A | **Stitched shell + pressure inflation** (recommended) | Triangulation + welding + ~300–500 lines of XPBD | Pouches, bags and garments with one algorithm; soft, dummy look is acceptable |
| B | **Rigid panels + hinge folding** | Triangulation + welding + a fold-angle solve | Excellent for boxy pouches and totes, poor for anything that must curve; needs a target angle per seam |
| C | **Project the flat layout onto a primitive** (box, cylinder) | Per-pattern mapping authoring | Fragile; every new shape needs new mapping rules |
| D | **Fake 2.5D** (offset, shadow, fold lines) | Hours | Cheap, but not a preview of the sewn object |
| E | **Full cloth simulation** (gravity, collisions, self-collision) | Weeks, tuning, GPU budget | Explicitly out of scope |

B is the fallback if A's tuning proves expensive: it is the same pipeline minus the
relaxation, so A's triangulation and welding work is not wasted either way.

## What the seam model already guarantees

| The preview needs | Where it comes from | Status |
| ----------------- | ------------------- | ------ |
| Which edge runs sew to which | `Assembly.seams[].sides[]` | Ships with the seam feature |
| Which end aligns to which | seam start = side 0's run start; `reversed` per side | Ships; explicit contract |
| Layer order (which panel is on top) | `sides` order | Ships |
| Ease handling | `eased` boolean; even distribution | Ships; shape is additive |
| Openings / boundaries | `finishedEdges` | Ships |
| Panel geometry | `resolveSeamSide`, `pieceEdgeSegments` | Ships; bridges included |
| Shells (connected groups) | derived from the seam graph | Add a helper in the preview |
| Notch alignment pins | existing notch marks, resolvable per edge | No change needed |
| Zipper | modelled as a seam | Convention, documented in the glossary |

## Preparation now (already applied to the seam spec)

1. **Corner-round bridges belong to a seam side.** A run that crosses a rounded
   corner includes the bridge in its length and its vertex correspondence.
2. **Canonical seam start and `reversed`.** Side 0's run start is the seam start;
   every other side is traversed from its start, or from its end when reversed.
3. **`resolveSeamSide` is the solver's input**, returning assembly-space points,
   `reversed` and `length` — not a check-only helper.
4. **Zipper convention.** A zipper is a seam (tape edges sewn to each other or to a
   strip), so a pouch stays a closed shell; marking both sides `opening` would let
   pressure leak.
5. **Renderer decision before the preview spec** (ADR): three.js as a lazy chunk
   amends the "SVG only" stack rule consciously; the solver lives in
   `@sewcraft/geometry`.

Deliberately **not** prepared: a seam `kind`, ease distribution shape, fabric face,
thickness, body collider, collision, animation, saved camera or pose, 3D export.
Each is additive.

## Staged roadmap

- **P0 — Wireframe shell.** Triangulate, weld, render the sewn shell without
  inflation. Proves the correspondence; a "net in 3D" is already informative.
- **P1 — Inflate.** Pressure XPBD, boundary capping, the Inflate slider. This is
  the pouch preview.
- **P2 — Materials.** Thickness offset, seam lines, zipper strip rendering, piece
  colours.
- **P3 — Dummy body.** Capsule/ellipsoid collider and shrink-wrap for garments.
- **P4 — Polish.** Pose presets, PNG export, a saved camera.

## Open questions

1. Renderer: three.js (recommended) versus a software rasteriser or SVG-only?
2. Placement: a full-screen dialog from the assembly ribbon, or its own route?
3. Does the first preview need a seam `kind` so a zipper can render as a strip, or
   is a seam line enough?
4. Open boundaries: cap them, or leave the shell open until P3?
5. Interactive inflation (drag a slider, re-relax each frame) or a fixed result
   with a Recalculate button?
